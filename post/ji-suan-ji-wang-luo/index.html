经典问题，为什么tcp要三次握手，4次挥手？
三次握手：电脑（SYN）->服务器 服务器（SYN+ACK）->电脑 电脑（ACK ）->服务器（防止服务器超时重传）
这样每一个设备都完成了确认自己有首发功能
四次挥手：（假如电脑关闭）电脑（FIN+ACK）->服务器 服务器（ACK）->电脑 (等待两条链路彻底没东西) 服务器（FIN+ACK）->电脑 电脑（ACK->服务器 此刻服务器这个端口就被释放出来了，可以使用了，但是电脑这个端口要等待一定时间才能释放，除非设置了端口复用不然无法继续使用直到释放。

应用层，负责向用户提供一组应用程序，比如 HTTP、DNS、FTP 等;
传输层，负责端到端的通信，比如 TCP、UDP 等；
网络层，负责网络包的封装、分片、路由、转发，比如 IP、ICMP 等；
网络接口层，负责网络包在物理网络中的传输，比如网络包的封帧、 MAC 寻址、差错检测，以及通过网卡传输网络帧等；

4.1 TCP如何连接

为什么tcp要三次握手，而不是四次，两次？

因为三次已经满足要求，所以不需要四次及以上次数。因为三次握手才能保证双方具有接受和发送的能力（这个两次也可以）。更重要原因如下（核心就是把确定是否连接的权力交给发起连接请求的人）：
1、三次握手可以阻止重复历史连接
场景：客户端发送SYN（seq=90），但是再传输过程阻塞超时，客户端重启然后发送SYN（seq = 100），
注意是重启不是重传，重传的话SYN的seq序列号是一样的。然后上面那个旧的先到，服务器回复SYN+ACK，结果Ack Num=90+1，但是客户端想要的是101，但是此时服务端这个端口已经建立连接了。所以客户端发送RST报文终止连接，然后才能成功。如果只有两次，服务端每收到一个SYN就只能主动建立一个连接，假如SYN阻塞，重复发送多次SYN报文，服务器会建立多个冗余连接，两次无法避免资源浪费。

此时有一个问题，假如在服务器回复SYN+ACK的时候，客户端接收到进入连接状态，然后发送ACK信号，服务器如果一直接受不到怎么办？下一个客户端的数据包会带上ACK+SEQ和上次一样，如果一直服务器收不到就会超时重传断开。假如客户端静默了服务器就会认为超时，继续超时重传断开ACK+SEQ。

2、同步双方初始序列号
序列号作用：1、接收方可以去除重复数据。2、接收方根据数据包序列号按序接受。3、可以标识发出去数据包，那些事已经被对方收到。

小结： TCP建立连接时，通过三次握手能防止历史连接的建立，能减少双方不必要的开销，能帮助双方同步初始化序列号。序列号能保证数据包不重复、不丢弃和按序传输。
不使用两次：无法防止历史连接建立，会造成双方资源浪费，也无法可靠同步双方序列号。
不使用四次：三次已经足够。

为什么每次TCP连接时，初始化序列号不一样？

防止历史报文被接受，为了安全性防止黑客伪造相同序列号TCP报文被接受。初始序列号采用ISN随机生成算法：SN = M + F(localhost, localport, remotehost,remoteport)。M是一个计时器，每隔4us加1，F是一个Hash算法，可以用MD5。

既然IP会分片，为什么TCP层还需要MSS？

MTU：一个网络包最大长度，以太网一般1500字节。
MSS：出除去IP和TCP头部，一个网络包能容纳TCP数据最大长度。
如果TCO整个报文（头部+数据）给IP层分片，那么IP层切片传输后，只要一个IP分片丢失，整个IP报文的所有分片都得重传。

握手信号缺失

第一次握手信号缺失： 只是客服端不断发送第一次握手信号，次数固定按照1s，2s，4s倍数增长。在达到tcp_syn_retries 次数后，不会再发了等待上一次超时时间两倍，客户端就会断开连接。（cat /proc/sys/net/ipv4/tcp_syn_retries）。
第二次握手信号缺失： 服务器和客户端都会重新发送，分别是发送第二次握手信号和第一次握手信号。第二次握手信号发送次数是（cat /proc/sys/net/ipv4/tcp_synack_retries）。
第三次握手信号缺失： 客户端接收到第二次握手信号，会发送ACK信号，假如服务器没接收到就会自动重传第二次握手。

SYN攻击

就是通过不停向服务器发送SYN请求包，把服务器半连接队列弄满导致其他程序无法连接。半连接队列就是服务器就受到SYN信号，就放入SYN队列然后发送SYN+ACK，如果收到了SYN第三次握手信息就放入Accept队列。解决这个攻击有三种方法：1、调大 netdev_max_backlog，就是接受网络数据包缓冲区。2、增大TCP半连接队列。3、开启 net.ipv4.tcp_syncookies，就是半连接满了，不放在半连接了，通过上面哈希值计算作为序列号传入，然后如果发送方回复了，那就代表成功没问题。4减少SYN-ACK重传目的。

TCP如何断开

客户端 (FIN，FIN_WAIT_1)-> 服务器
服务器(ACK，CLOSE_WAIT)->客户端（FIN_WAIT_2）
服务器(FIN，LAST_ACK )->客户端
客户端(ACK，TIME_WAIT )->服务器段（CLOSE）
注意谁主动关闭连接的，才有TIME_WAIT状态，和前面一样，ACK报文是不会重传的。

为什么挥手需要四次？

客户端发送FIN，说明客户端不会再发但是会接受。服务器发送ACK表示收到了，我先把还要发给你处理完。处理完成后服务器发送FIN信号说明我要发给你的发完了，此时客户端接受到了说ok你关闭吧，我还等一会把你发的信息处理完。服务器端接收到ACK直接关闭，客户端经过2MSL后进入关闭状态。
注意，CLOSE_WAIT 状态没有设置任何超时定时器。
第一次挥手丢包（Client 发 FIN 丢失）：
客户端处于 FIN_WAIT_1，启动超时重传 FIN（受 tcp_orphan_retries 控制）。达到上限后强制释放本地连接。服务端处于不知情的 ESTABLISHED，无心跳机制时会永久挂死。

第二次挥手丢包（Server 回 ACK 丢失）：
服务端已进入 CLOSE_WAIT。客户端因没收到 ACK 继续重发 FIN。服务端收到重发的 FIN 会再次补回 ACK。服务端应用层执行 close() 后发出第三次挥手的 FIN 并切入 LAST_ACK，最终在客户端跑路、等不到第四次 ACK 的情况下超时强制释放。

第三次挥手丢包（Server 发 FIN 丢失）：
服务端处于 LAST_ACK 状态，超时重传 FIN 直到达到最大重试次数后强制释放。客户端此时若处于 FIN_WAIT_2（且执行的是 close），受 tcp_fin_timeout（通常 60 秒）控制，超时后强制释放。

第四次挥手丢包（Client 回 ACK 丢失）：
客户端已进入 TIME_WAIT 倒计时（2MSL）。纯 ACK 不会启动主动重传；而是服务端因收不到 ACK 重传第三次挥手的 FIN。客户端收到重传的 FIN 后被动补发 ACK 并重启 2MSL 计时。若重传链路彻底瘫痪，服务端重试 FIN 耗尽后在 LAST_ACK 强制销毁，客户端等待 2MSL 倒计时结束后自然销毁。

为什么需要 TIME_WAIT 状态？

主动发起关闭连接的一方，才有TIME-WAIT状态。需要这个状态是为了让两个方向上数据包都被丢弃，是的下一次再出现的数据包一定是新建立的。还有让被动关闭的一方优雅关闭，假如客户端直接关闭，服务器段再次发送第三次挥手信号，在超时之前直接客户端回复一个RST信号，服务器上层可能爆出异常错误。
优化TIME_WAIT状态
1、开启tcp_tw_reuse与tcp_timestamps，假如connect满了，系统会把处于TIME-WAIT状态超过1s的端口直接拿来用，开启时间戳就能防止历史数据残留进来。
2、系统最大允许tcp_max_tw_buckets个TIME-WAIT状态，如果超过了就不要2MSL等待了，直接TCP: time wait bucket table overflow。可以把这个值调大。
3、直接代码里面是要SO_LINGER发送RST，直接强制双方断开。

客户端的connect是在第二次握手后，然后服务端的accept是在第三次握手成功之后。
客户端调用close，发送了FIN报文，然后服务端收到FIN，会插入一个EOF咋接收缓冲区，然后应用程序read这个FIN包，读取到EOF的时候也是用close发送FIN包(这代表你必须read函数必须判断还有close，不然会出现很多TIME_WAIT)，随后第四次挥手。

TCP快速建立连接，常规是三次握手+HTTP GET+ 返回data，一共5*0.5=2.5RTT，但是最后一次握手时可以携带数据的，把HTTP GET放在第三次挥手，节省了一次变成2RTT。linux内核开启了 TCP Fast Open 功能，就是刚开始使用2次RTT，这个过程传输了一个cookie，然后的日子请求的时候三次握手那些就没了，直接一个SYN+cookie然后ACK就连接上了，整个耗时1RTT。

4.2 TCP重传

超时重传：

RTT 数据发送时刻到接受到确认的时刻的时间差值。比如客户端发送SYN信号，直到客户端接收到SYN+ACK信号时间差值。
RTO 超时重传时间。RTO应该略大于RTT时间，应为RTO较大，重发太慢没有效率。RTO较小，可能没丢包就重发导致重发太多使得网络更加拥塞。
RFC6289 建议使用以下的公式计算 RTO，不仅滑动滤波RTT，也滑动滤波RTT的变化量。

快速重传：

以数据驱动重传，根据ACK信号，假如我发送Seq1 2 3 4 5，结果只发送了Seq1 3 4 5，他在后面3，4，5只会一直回复ACK 2，直到收到Seq 2，连续收到三次这个Ack 2再次回复数据Seq2。
但是，面临一个问题重新传输1个还是后面所有，这时候通过SACK，这个回复包含已经接收到的信息，比如上面的例子回复[3,5]。

滑动窗口：

发送方滑动窗口
#1、已发送数据并受到ACK
#2、已发送但是未收到ACK
#3、未发送但总大小在接收方处理范围
#4、未发送总大小超过接收方处理范围

程序通过三个变量来，发送窗口SND.WMD，发送窗口大小（接收方指定），SND.UNA（指向#2的第一个字节），SND.NXT（指向#3的第一个字节），所以可用窗口大小就是现在#3的大小，计算公式为可用窗口大小 = SND.WND -（SND.NXT - SND.UNA）

接收方滑动窗口
#1 #2、已成功接收到并确认的数据（等待应用进程读取）
#3、未 收到的数据，但可以接受
#4、未收到数据，并不可以接受
三个接收部分两个指针就可以划分，RCV.WND表示接受窗口大小，RCV.NXT是#3的第一个字节。

注意如果发生了先减少缓存，再收缩窗口，就会出现丢包的现象。为了防止这种情况，TCP规定不允许同时减少缓存和收缩窗口，而是先收缩窗口再减少缓存。

窗口关闭

如果窗口大小为0，就会阻值发送方给接收方传递数据，直到窗口变为非0为止，这就是窗口关闭。
窗口关闭后，发送方会进行等待接收方处理信息后，窗口大小不为0回复ACK包。但是如果ACK包传输过程丢失就会产生死锁现象。
接收方会启动一个持续定时器，发送窗口探测报文，对方接收到这个报文返回自己的窗口大小。

糊涂窗口综合征

如果接收方现在只有几个字节窗口大小了，结果发送方每次发送几字节，但是TCP+IP头部都至少40字节了。这也就是不太划算。解决方法是：要么接收方不通告小窗口，要么发送方不发送小数据。
发送方策略：Nagle算法，该算法是延时处理，伪代码如下

if 有数据要发送{
    if 可用窗口大小 >= MSS and 可发送的数据 >= MSS{
        立刻发送MSS大小的数据
    } else {
        if 有未确认的数据 {
            将数据放入缓存等待接收ACK
        } else {
            立刻发送数据
        }
    }
}

接收方得满足「不通告小窗口给发送方」+ 发送方开启 Nagle 算法，才能避免糊涂窗口综合症。不然发送小窗口会满足Nagle算法的下面条件。

接收方策略：David D. Clark 算法（别乱通告小窗口）
规则：当接收缓冲区有空位时，只要空位还没达到一个最大报文段大小（MSS，通常约 1460 字节），或者还没达到接收缓冲区总容量的一半（50%），就坚决通告 Window = 0！

效果：哪怕应用程序读走了 2 个字节，内核也装作没空位，憋着不发通告，直到应用程序攒够读出一大批空间，才一口气通告一个大窗口给对方。

拥塞控制

swnd = min(cwnd,rwnd)，cwnd就是拥塞窗口，他是根据网络的拥塞程度动态变化的。

4.3 抓包分析

TCP三次握手第一次没发送过去，就会一直重复发送。
TCP第二次握手没发送过去，第一次握手会重发，而且每次收到SYN第二次握手都会重发，然后第二次握手也会有一个重发操作，直到重发次数达到最大再继续重发。
TCP第三次握手没发过去，客户端发送一次ACK，服务区会发送SYN_ACK直到超时。TCP建立连接后的数据包传输，最大超时重传次数是由 tcp_retries2 指定，如果还是传不过去，客户端就会断开ESTABLISHED 。如果没有数据传输就会开启TCP保活机制，就是上面说的探测报文。

4.4 半连接队列和全连接队列

服务段可以使用ss命令查看TCP全连接队列，除注意ecv-Q/Send-Q 在「LISTEN 状态」和「非 LISTEN 状态所表达的含义。Recv-Q：当前全连接队列的大小，也就是当前已完成三次握手并等待服务端 accept() 的 TCP 连接。Send-Q：当前全连接最大队列长度。
非LISTEN状态所表达的含义：Recv-Q：已收到但未被应用进程读取的字节数；Send-Q：已发送但未收到确认的字节数；

全连接爆满
当服务器并发处理大量请求，如果TCP全连接队列数量过小，发生TCP全连接溢出时，后续请求就会被抛弃。也可以选择向客服端发送RST复位报文，根据/proc/sys/net/ipv4/tcp_abort_on_overflow，这个值0就默认行为抛弃，1就是发送RST报文。0的话能让服务器更好处理突发请求过多,比较温和。
全连接队列最大值是sk_max_ack_backlog变量，sk_max_ack_backlog 实际上是在 listen() 源码里指定的，也就是min(somaxconn, backlog)；

半连接爆满
如果半连接队列满了，没有开启tcp_syncookies，直接丢弃。
如果全连接满了，而且没有重传 SYN+ACK 包的连接请求多于 1 个（说明外部持续有设备想要连接，网络过载并非偶然），则会丢弃。
如果没有开启tcp_syncookies，且max_syn_backlog减去 当前半连接队列长度小于(max_syn_backlog >> 2)（只剩25%），则会丢弃；

四次挥手中收到乱序的FIN包会如何处理？（shutdown只关闭写端）
因为 TCP 是严格面向保序字节流的协议，FIN 标志位本身在协议中占用 1 个字节的序列号。当第三次挥手的 FIN 报文因为网络乱序先于前面的数据到达时，主动方内核检测到存在序号空洞，不会直接处理该 FIN，也不会直接进入 TIME_WAIT 状态，而是将这个乱序的 FIN 报文暂存在**乱序队列（ofo queue）**中。 当滞后的数据包到达补齐空洞后，数据会被送入接收队列供应用层正常读取；随后内核自动激活处理乱序队列中的 FIN 报文，回复第四次挥手 ACK 并正式转入 TIME_WAIT 状态。”

4.11

在 TIME_WAIT 状态的 TCP 连接，收到 SYN 后会发生什么？ 所以这一题怎么简短回答
核心定性：处于 TIME_WAIT 的连接收到相同四元组的 SYN 报文时，Linux 会依据时间戳（PAWS）或序列号判断其合法性。

合法情况（时间戳单调递增，或未开启时序列号大于期望值）：服务端判定为新发起的合法连接，直接复用该连接跳出 TIME_WAIT，状态切为 SYN_RECV 并回送 SYN+ACK 完成正常握手。

非法情况（时间戳倒退，或未开启时序列号小于等于期望值）：服务端判定为网络迷途旧包，直接丢弃该 SYN 报文，并回送一个 Challenge ACK（携带旧连接进度）；客户端收到后因状态不匹配会回复 RST，进而将服务端该 TIME_WAIT 连接彻底关闭。

HTTP缓存

强缓存，响应码 200。通过http响应头部Response Header实现，表示资源在客户端缓存有效期：Cache-Control是相对时间，Expires是绝对时间，Cache-Control优先级高于Expires。客户端下次访问这个，会看数据有没有过期，没有直接用这个缓存，有就再次发送数据给服务器。
协商缓存，响应码304，有两种方式实现，第一种是请求头部If-Modified-Since，值位上一次修改时间，上传给服务器，响应头部为Last-Modified，表示这个响应资源的最后修改时间。如果过期，响应码200，无更新响应码304。第二种请求头部为If-None-Match，值为上一次Etag，当资源过期，客户端传输，服务器返回最后Etag,如果过期，响应码200，无更新响应码304。
Etag优先级更高，因为第一种只能精确到s，还有内容不更改最后修改时间改了，服务器也可能不能精确获取文件修改时间。

TLS第二次握手
服务端收到客户端打招呼，会返回Server Hello消息，服务器回确认TLS版本号，服务器的随机数，以及服务端选择的密码套件。
服务器为什么证明自己身份，会下发证书给客户端，因为服务器选择ECDHE密钥协商算法，发送完证书后，发送Server Key Exchange消息，包含椭圆曲线公钥。最后返回Server Hello Done。
TLS第三次握手
客户端根据自己的随机数，生成椭圆曲线公钥，发送给服务器，这个时候双方都能计算出最终的会话密钥。
然后客户端发送Change Cipher Spec，告知双方加密通信。
最后客户端吧之前发的数据加密做一个加密，给服务器验证。
TLS第四次握手Change Cipher Spec，告知双方加密通信，然后也把之前发的数据加密，给客户端验证。（验证双方解密能力，防止数据中间被人篡改比如明文数据）
这个问题中间被人篡改明文信息被TLS1.3解决一部分，就是开头猜测对方使用椭圆算法，把自己生成椭圆密钥发过去了，对方收到直接生成会话密钥，然后发送自己椭圆密钥，客户端也生成相同会话密钥直接计算。

3.5 HTTPS如何优化

会话复用

第一种叫Sesion ID，这个由服务器保存id值，里面根据id值查到会话密钥，但是这个缺点就是当有几百万个连接，服务器内存消耗太大。
第二种叫Session Ticket，服务器把缓存任务给了客户端，下一次复用，客户端把服务器生成的Ticket发过来，然后服务器根据自己内部某把密钥解开这个，获得会话密钥。这两种方法都有前向危机。因为拿到这个Ticket密钥可以解出来会话密钥，此时ECDHE算法优势荡然无存。
TLS1.3直接重连的时候，把HTTP请求和Ticket直接一起发送，0RTT延迟，上面还有一个RTT延时。但是这里有重放攻击危险，假如一个POST请求，在这里不断重发数这里重连+POST的数据包，然后服务器没检验直接出问题。避免重放攻击就是给对话密钥设定一个合理过期时间。

证书优化

服务器精良选用ECDSA证书而不是RSA证书，相同安全级别ECDSA密钥长度比RSA短，证书传输效率提高。
服务器开始OCSP Stapling功能，服务器每隔一段时间获得OCSP响应，然后跟证书一起发给客户端，客户端就知道这个网站有效时间。

HTTP3优化方面

无队头阻塞

QUIC协议类似HTTP/2 Stream与多路复用，但底层的QUIC使用的是UDP（消除了传输层头部阻塞）。

更快连接建立

HTTP1/2都需要tcp三次握手TLS四次握手，而HTTP/3传输数据只要QUIC握手，只要一个RTT，因为它支持椭圆算法，第一次就传输过去密钥等待混合。

更快连接迁移

TCP基于四元组，如果从4G切换成WIFI，IP地址变了要重连，然后TCP慢启动，但是QUIC直接通过连接ID标记两个端点，就算IP变了，ID，TLS密钥还在迅速重连。

为了解决这个问题，QUIC建立转悠电报，叫Encoder Stream（编码单向流）：专门用来发“字典更新指令”。 Decoder Stream（解码单向流）：专门用来回“确认已同步”。
客户端通过Encoder Stream单独发送插入表指令，比如插入useragent，然后服务器收到，通过Decoder Stream回复。后面服务器就可以用这个索引给各个流发送信息了。
***如果客户端“等不及”服务器确认怎么办？***这里还有一个细节：如果客户端每加一个动态表都要等服务器回确认，那不就多浪费了一个往返时延（RTT）吗？QPACK 非常灵活，支持两种模式：
保守模式（零阻塞保证）：严格等 Decoder Stream 回了 ACK 确认后，业务流才开始使用该表项（彻底消灭队头阻塞）。
激进模式（带风险推测）：客户端直接在 Encoder Stream 刚发完表项后，就立即在业务流里引用。如果此时网络一切正常，享受极高压缩率；如果发生了丢包，QPACK 规定仅阻塞引用了该表项的具体某一个流，其他没有引用该表项的普通流（比如只引用静态表的流）依然全速运行，绝不连带卡死。

为了让TIME_WAIT状态连接被快速回收，开启了两个。net.ipv4.tcp_tw_reuse开启的花，相同四元组连接直接看上一次这个连接TIME_WAIT是否持续1秒，如果是就重用这个。
net.ipv4.tcp_tw_recycle现在不推荐使用，因为NAT下可能因为各个机器开机时间不一致导致连接不了，比如机器A时间1000，机器B时间100，他们经过NAT都是相同ip出去，但这个不检验你的端口只看ip，他认为1000就是最新时间，100就是旧包。这两个都要开启TCP时间戳。

半连接队列满了，会丢弃syn，除非开启cookies。全连接满了直接丢弃ack信号或者直接rst，全连接满了哪怕半连接没满也会直接丢弃syn

客户端掉线，上线继续发SYN给服务端
客户端发送SYN端口号不一样，四元组自然不同，可以连接，原本连接可通过保活机制或者服务器发送数据客户端返回RST终止。
客户端发送SYN端口号一样，四元组一样，客户端返回上一次正常的seq和ack，结果客户端不认识直接rst。

在TIME_WAIT状态，如果出现SYN信号，必须判断seq和timestamp都大于上一次的，或者只有seq大于（没有开启时间戳）

什么时候四次挥手变成三次
没有数据要发送给客户端或者开启TCP 延迟确认机制

NAT缺点和解决方案
缺点：一断电路由表丢失，路由表增改有开销，外部无法连接设备，只能等设备来连接。
解决方案：使用ipv6，使用NAT穿透技术（将这个映射给设备，就相当于NAT只做转发）

127.0.0.1 是回环地址。localhost是域名，但默认等于 127.0.0.1
ping 回环地址和 ping 本机地址，是一样的，走的是lo0 "假网卡"，都会经过网络层和数据链路层等逻辑，最后在快要出网卡前狠狠拐了个弯，数据插入到一个链表后就软中断通知 ksoftirqd 来进行收数据的逻辑，压根就不出网络。所以断网了也能 ping 通回环地址。
如果服务器 listen 的是 0.0.0.0，那么此时用127.0.0.1和本机地址都可以访问到服务。
