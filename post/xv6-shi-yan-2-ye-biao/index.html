xv6实验[2]-页表Superpages内核实现

2026-06-06 12 min read

1. 实验背景与题目要求

在标准的 RISC-V Sv39 架构下，xv6 内核采用三级页表管理，默认的内存分配粒度是 4KB4\text{KB}4KB（4096 字节4096\text{ 字节}4096 字节）。

本次实验的级核心要求是：改造内核的内存管理链路，使其支持 2MB 的大页面（Superpages）分配。具体场景为：当用户程序调用 sbrk(n) 动态申请内存，且申请大小达到 2MB 或更多时，如果当前的堆顶虚拟地址刚好满足 2MB 对齐，内核应当直接分配一整块连续的 2MB 物理大页并完成二级页表映射，而不是繁琐地去调用 512 次 kalloc 分配 4KB 的小页。

2. 核心机理：为什么大页偏偏是 2MB？

在着手写代码前，我首先理清了 RISC-V 硬件寻址的数学逻辑。为什么大页的尺寸硬性规定必须是 2MB，而不是 1MB 或 16MB？秘密就隐藏在 Sv39 的三级页表（L2、L1、L0）索引结构中。每一级页表包含 512 个页表项（PTE），每个底层叶子节点管理 4KB 空间。因此，当我们遍历到中间页表（二级页表，即 L1 级）的某一个槽位时，它底下的那张 L0 页表一旦完全展开，其管辖的虚拟地址空间天然就是：

512×4096 Bytes=2,097,152 Bytes=2MB512 \times 4096 \text{ Bytes} = 2,097,152 \text{ Bytes} = 2\text{MB} 512×4096 Bytes=2,097,152 Bytes=2MB

RISC-V 硬件设计者在底层留了一个“走捷径”的后门：原本 MMU 寻址需要无脑向下钻完三级（L2 -> L1 -> L0）。但如果在 L1 级页表项上直接设置了读、写或执行权限（即判断为 PTE_LEAF），MMU 硬件就会立刻触发刹车机制，停止下钻。它会直接认定：当前项指向的是一整块连续且 2MB 对齐的超级页面。在工业界（如 Linux 的透明大页 THP 机制），这种设计能将 512 个 TLB 缓存表项压缩为 1 个，大幅降低大内存消耗型应用的 TLB Miss 率，具有极高的工程价值。

3. 代码实操

物理内存布局的静态分区 (Static Memory Partitioning)

原生内核在启动执行 kinit() 时，默认将从内核代码段结束（end）至物理内存上限（PHYSTOP）之间的所有可用空间，全部按 4KB 粒度初始化至单一的空闲链表中。
为了满足大页分配的连续性要求，我在此处引入了静态内存分区设计。在系统初始化早期，强行将物理内存的高地址区域（即 PHYSTOP 向下偏移 16MB 的空间）划分为独立的大页专属内存池，而剩余的低地址区域继续沿用原生 4KB 分配逻辑。这种设计既保证了大页内存的绝对物理连续性，又最大程度减少了对原生小页管理逻辑的侵入。

void
kinit()
{
  initlock(&kmem.lock, "kmem");
  superkinit();
  uint64 super_start = PHYSTOP - (16 * 1024 * 1024);
  freesuperrange((void *)super_start, (void *)PHYSTOP);
  freerange(end, (void*)super_start);
}

大页内存的初始化与硬件对齐约束

在按块切分大页池时，必须严格遵守 RISC-V 架构的硬件规范：Superpage 的物理首地址必须按 2MB 边界严格对齐。 为此，我在 freesuperrange 初始化函数中，引入了 SUPERPGROUNDUP 宏进行地址的向上对齐校验，并以 SUPERPGSIZE（2MB）为步长，将这片空间切割后逐一挂载至大页空闲链表。

void freesuperrange(void *pa_start, void *pa_end)
{
  char *p;
  // 核心约束：强制物理地址以 2MB 向上对齐，满足 MMU 寻址规范
  p = (char*)SUPERPGROUNDUP((uint64)pa_start);
  
  // 以 2MB 为步长遍历并释放至大页空闲链表
  for (; p + SUPERPGSIZE <= (char *)pa_end; p += SUPERPGSIZE)
    superkfree(p);
}

内存申请和释放

拿到 16MB 的大页内存池后，第一步是实现底层的 alloc 和 free。申请内存的逻辑其实很简单，用了一把自旋锁保护，直接从链表头部摘一个节点下来就行

void * superkalloc(void)
{
  struct run *r;
  acquire(&super_kmem.lock);
  r = super_kmem.freelist;
  if(r)
    super_kmem.freelist = r->next;
  release(&super_kmem.lock);
  if(r)
    memset((char*)r, 5, SUPERPGSIZE); // 填充垃圾数据，防止旧数据残留
  return (void *)r;
}

作为底层内核代码，内存释放函数 superkfree 极易成为系统崩溃的重灾区。在实现该模块，参考原内核kfree代码，在将物理块重新插入 super_kmem.freelist 单链表之前，代码会执行三项严格的安全校验，并在挂载前主动填充特定标志位.

void superkfree(void *pa)
{
  struct run *r;
  // 内核安全边界断言：
  // 1. 校验物理地址是否严格满足 2MB 对齐
  // 2. 校验地址是否非法越界踩入内核代码段 (pa < end)
  // 3. 校验地址是否越出物理内存硬件上限 (pa >= PHYSTOP)
  if(((uint64)pa % SUPERPGSIZE) != 0 || (char *)pa < end || (uint64)pa >= PHYSTOP)
    panic("superkfree: Invalid physical address");
  // 内存污染机制：填充特定特征值 (0x01)
  // 目的：在发生 Use-After-Free 非法访问时，促使程序产生确定性异常，便于 Debug
  memset(pa, 1, SUPERPGSIZE);
  r = (struct run*)pa;
  // 临界区保护：获取自旋锁，采用头插法将物理块挂入大页空闲链表
  acquire(&super_kmem.lock);
  r->next = super_kmem.freelist;
  super_kmem.freelist = r;
  release(&super_kmem.lock);
}

在 uvmalloc 中“截胡”：优先分配大页

用户程序调用 malloc 时，底层最终会走到 sys_brk，并通过 uvmalloc 来实际分配物理内存。我在这里加上了“优先尝试大页”的拦截逻辑。
如果用户申请的空间满足 2MB 对齐，且大页池子里还有空闲就优先用大页；如果大页分配失败（比如池子空了），不要直接报错，而是老老实实退回到原本分配 4KB 小页的循环里去。

uint64 uvmalloc(pagetable_t pagetable, uint64 oldsz, uint64 newsz, int xperm)
{
  char *mem;
  uint64 a;
  int sz; // 动态步长
  if(newsz < oldsz) return oldsz;
  oldsz = PGROUNDUP(oldsz);
  for(a = oldsz; a < newsz; a += sz){
    // 拦截条件：地址 2MB 对齐，且剩余所需空间至少有 2MB
    if ((a % SUPERPGSIZE) == 0 && (a + SUPERPGSIZE <= newsz))
    {
      mem = superkalloc();
      if (mem != 0)
      {
        memset(mem, 0, SUPERPGSIZE);
        // 尝试映射大页，注意补齐 PTE_R 和 PTE_U (用户态访问权限)
        if (mapsuperpages(pagetable, a, SUPERPGSIZE, (uint64)mem, PTE_R|PTE_U|xperm) != 0)
        {
          superkfree(mem); // 映射失败，及时回收物理大页
        }
        else
        {
          sz = SUPERPGSIZE; // 映射成功，步长直接跨越 2MB！
          continue;
        }
      }
    }
    // 如果不满足大页条件，或者大页分配/映射失败，退回到普通的 4KB 分配逻辑
    sz = PGSIZE;
    mem = kalloc();
    if(mem == 0){
      uvmdealloc(pagetable, a, oldsz);
      return 0;
    }
#ifndef LAB_SYSCALL
    memset(mem, 0, sz);
#endif
    if(mappages(pagetable, a, sz, (uint64)mem, PTE_R|PTE_U|xperm) != 0){
      kfree(mem);
      uvmdealloc(pagetable, a, oldsz);
      return 0;
    }
  }
  return newsz;
}

直接在 L1 页表上映射

既然分配了大页，就不能用原版的 mappages 去一层层映射到 L0 了。我单独写了一个 mapsuperpages 函数。 它的逻辑非常直接：先查 L2 目录，如果去 L1 的路没通，就分配一个 4KB 的页作为 L1 的目录。找到 L1 的槽位后，直接把 2MB 物理大页的地址和权限盖在这个槽位上。 根本不去管 L0 层。

int mapsuperpages(pagetable_t pagetable, uint64 va, uint64 size, uint64 pa, int perm)
{
  pte_t *pte;
  // 严格的对齐校验
  if((va % SUPERPGSIZE) != 0) panic("mapsuperpages: va not aligned");
  if((size % SUPERPGSIZE) != 0) panic("mapsuperpages: size not aligned");
  if(size == 0) panic("mapsuperpages: size");
  // 1. 查找 L2 级目录
  pte = &pagetable[PX(2, va)];
  pagetable_t l1;
  
  if (*pte & PTE_V) // 如果 L1 目录已存在
  {
    l1 = (pagetable_t)(PTE2PA(*pte));
  }
  else { 
    // 不存在则分配一个 4KB 的普通页作为 L1 目录
    if((l1 = (pde_t *)kalloc()) == 0) return -1;
    memset(l1, 0, PGSIZE);
    *pte = PA2PTE(l1) | PTE_V;
  }
  // 2. 锁定 L1 级槽位
  pte_t *pte1 = &l1[PX(1, va)];
  if(*pte1 & PTE_V)
    panic("mapsuperpages: remap");
    
  // 3. 关键一步：直接在此处写入 2MB 大页的物理地址和权限，硬件识别到后会自动将此作为叶子节点
  *pte1 = PA2PTE(pa) | perm | PTE_V;
  return 0;
}

解除映射与进程克隆

原版的 uvmunmap 和 uvmcopy 都是按 4KB 步长死循环的。如果不做处理，它们遇到我刚才塞进去的 2MB 大页，会连续释放/拷贝 512 次相同的地址，系统当场 Panic。
解决办法是手动深入页表探测。在这两个函数的 for 循环里，先去 L1 层看一眼。如果 L1 的 PTE_V 有效，并且它带有读/写/执行权限（说明它是叶子节点，也就是大页），我就按 2MB 的逻辑处理，并且把循环步长 sz 动态修改为 2MB，跳过这段区域.

void uvmunmap(pagetable_t pagetable, uint64 va, uint64 npages, int do_free)
{
  uint64 a;
  pte_t *pte;
  int sz; // 引入动态步长

  if((va % PGSIZE) != 0) panic("uvmunmap: not aligned");

  for(a = va; a < va + npages*PGSIZE; a += sz){
    pte_t *pte2 = &pagetable[PX(2, a)];
    if (*pte2 & PTE_V)
    {
      // 手动剥开页表：拿到 L1 目录，看看对应的槽位是不是叶子节点
      pagetable_t l1 = (pagetable_t)PTE2PA(*pte2);
      pte_t *pte_1 = &l1[PX(1,a)];
      
      // 如果 L1 有效，并且具备终端权限 (R/W/X)，确认为 2MB 大页！
      if ((*pte_1 & PTE_V) && ((*pte_1 & (PTE_R|PTE_W|PTE_X)) != 0))
      {
        if (do_free) {
          superkfree((void *)PTE2PA(*pte_1)); // 释放整块大页
        }
        *pte_1 = 0;
        sz = SUPERPGSIZE; // 步长调成 2MB，跳过剩下的 511 次无用循环
        continue;
      }
    }

    // ... 下面是原版 4KB 小页的 walk 与 free 逻辑，步长 sz = PGSIZE
    sz = PGSIZE;
    if((pte = walk(pagetable, a, 0)) == 0)
        panic("uvmunmap: walk");
    if((*pte & PTE_V) == 0) {
        printf("va=%ld pte=%ld\n", a, *pte);
        panic("uvmunmap: not mapped");
    }
    if(PTE_FLAGS(*pte) == PTE_V)
        panic("uvmunmap: not a leaf");
    if(do_free){
        uint64 pa = PTE2PA(*pte);
        kfree((void*)pa);
    }
    *pte = 0;
  }
}

最后是 fork() 时触发的 uvmcopy 修改：逻辑和上面极其类似。如果检测到父进程这是块大页，就给子进程也批发一块大页，用 memmove 一次性拷贝 2MB，然后映射好。

int
uvmcopy(pagetable_t old, pagetable_t new, uint64 sz)
{
  pte_t *pte;
  uint64 pa, i;
  uint flags;
  char *mem;
  int szinc;
  for(i = 0; i < sz; i += szinc){    
    pte_t *pte2 = &old[PX(2, i)];
    if (*pte2 & PTE_V)
    {
      pagetable_t p1 = (pagetable_t)PTE2PA(*pte2);
      pte_t *pte1 =  &p1[PX(1, i)];
      if (*pte1 & PTE_V && ((*pte1 & (PTE_R|PTE_W|PTE_X)) != 0))
      {
        pa = PTE2PA(*pte1);
        flags = PTE_FLAGS(*pte1);
        if((mem = (char *)superkalloc()) == 0)
        {
          goto err;
        }
        memmove(mem, (char *)pa, SUPERPGSIZE);
        if(mapsuperpages(new, i, SUPERPGSIZE, (uint64)mem, flags) != 0)
        {
          superkfree(mem);
          goto err;
        }
        szinc = SUPERPGSIZE;
        continue;
      }
    }
    szinc = PGSIZE;
    if((pte = walk(old, i, 0)) == 0)
      panic("uvmcopy: pte should exist");
    if((*pte & PTE_V) == 0)
      panic("uvmcopy: page not present");
    pa = PTE2PA(*pte);
    flags = PTE_FLAGS(*pte);
    if((mem = kalloc()) == 0)
      goto err;
    memmove(mem, (char*)pa, PGSIZE);
    if(mappages(new, i, PGSIZE, (uint64)mem, flags) != 0){
      kfree(mem);
      goto err;
    }
  }
  return 0;
 err:
  uvmunmap(new, 0, i / PGSIZE, 1);
  return -1;
}

总结

走完这套流程——从物理内存的分区切分、分配时的动态拦截、底层页表的直接写死，再到进程解绑和克隆时的安全收尾——xv6 内核里这套大页（Superpages）的生命周期才算真正形成了闭环。
做完这个实验，我联想到了 Linux 内核庞大且精密的内存管理子系统。在 Linux 的世界里，kmalloc 的架构逻辑有着异曲同工之妙，但又远比这里复杂：大块的连续物理内存交由伙伴系统（Buddy System）大刀阔斧地统筹，而高频、细碎的小内存请求则交由 Slab/Slub 分配器去精雕细琢，外围还包裹着 TLB 刷新策略和各级 Cache 的极致优化。继续努力学习操作系统吧！
