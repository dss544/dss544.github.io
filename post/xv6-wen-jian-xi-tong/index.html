##孤儿文件导致磁盘空间泄漏
1、地毯式搜救
当系统崩溃重启后，操作系统不急着开机，而是先把把整个磁盘从头到尾完完整整地扫描一遍（在 Linux 里这个工具叫 fsck）。fsck会把“Bitmap 标记为已占用的块”和“所有文件夹里登记的文件名”进行对账。如果发现某个 inode 在磁盘上占着坑，但全磁盘没有任何一个文件夹包含它，那就判定它是“孤儿”，直接在开机前把它释放掉。
缺点：太慢，每次都要从头扫描磁盘。
2、孤儿链表
不需要扫描全盘。只要当一个文件的名字被删掉（nlink == 0）、但内存里还有人开着它（ref != 0）的那一瞬间，内核立刻在磁盘的一个固定特殊位置（比如 超级块 Superblock 或者日志区）的“小本本”上记下一笔：“报告，inode 编号 5 变成孤儿了！”正常结束：如果程序正常关闭了文件，内核把空间释放后，会顺手把小本本上的这行字擦掉。崩溃恢复：如果中途突然断电，重启时系统不需要扫描全盘，只需要直奔这个“小本本”。只要发现小本本上还留着 inode 编号 5，就知道它是个没来得及处理的孤儿，直接把它清空即可。
优点：极快，开机速度不受磁盘大小影响（现代 Linux 文件系统如 ext4、XFS 均采用类似机制）。

##防止文件并发撞车
线程A在查/a/b的时候，会先把a的锁释放 在取申请b的锁（为什么不先申请b在释放a呢？我的理解是可能导致死锁 比如线程1要在/a 要去/b就要获取/b的锁 而线程2在/a/b 要去/a 就要申请a的锁，结果两个线程互锁导致死锁）。但此时可能回来一个线程B，他速度更快获取/a的锁然后删除了b。此时线程A还没来得及给b加锁（处于真空期），结果第三个线程来了，通过balloc正好申请到b这个物理内存，用来存文本数据。这是A醒来发现目录b变成文本文件了，但他还是用struct dirent数组来解析，就会导致错误。
xv6的解决方法：线程A在释放/a的锁之前，先找到b的inum，然后使用iget把b的应用计数加1在释放掉/a的锁，这样此时线程B就无法删除它，因为unlink函数中调用iput释放空间的条件是if(ip->ref == 1 && ip->valid && ip->nlink == 0)，所以线程B只能让nlink为0，ref--，而不能删除数据块。

🔗 Linux 硬链接与软链接核心特性对比

在 Linux/Unix 系统中，**硬链接（Hard Link）和软链接（Soft Link/Symbolic Link）**是两种完全不同的“文件别名”机制。为了方便对比理解，它们的底层区别和特性已汇总在下表中：

特性 硬链接 (Hard Link) 软链接 (Soft Link / Symbolic Link)
Inode 编号 与源文件相同
(共享同一个物理文件真身)		 与源文件不同
(自己是一个独立的新文件)
磁盘空间 不占用额外空间
(仅在所属目录的数据块里多写一行记录)		 占用极小空间
(需要单独的磁盘块来存储目标路径字符串)
跨分区/跨盘 ❌ 绝对不行
(每个分区的 Inode 独立排号，无法跨盘映射)		 完全可以
(内部存的是路径字符串，顺藤摸瓜即可)
对目录使用 ❌ 绝对不行
(避免系统内部形成环路死循环，内核严格禁止)		 完全可以
(非常适合为很深的文件夹创建快捷方式)
源文件被删后 完好无损
(只要文件的物理链接数 nlink > 0，数据就依然可访问)		 ❌ 链接失效
(变成“死链接”，类似于 Windows 快捷方式找不到源头)
创建命令 ln 源文件 硬链接名 ln -s 源文件 软链接名
(多了一个 -s 参数)

💡 快速记忆大白话场景模拟

我们可以把磁盘上的真实数据想象成一本真正的纸质书：

  • 硬链接：相当于你在它的封面上贴了两个名字标签（比如左边写《微积分》，右边写《大一教材》）。哪怕你把《微积分》这个标签撕掉，这本书依然完好无损地躺在那里，因为还有个《大一教材》的标签吊着它的命。
  • 软链接：相当于你在另一张独立的便利贴上写了一句话：“那本微积分教材在客厅第三个书架上”。如果你把那本真正的书一把火烧了，这张便利贴依然在，但你顺着便利贴上的话去找书时，只能看到一堆空气（死链接）。
